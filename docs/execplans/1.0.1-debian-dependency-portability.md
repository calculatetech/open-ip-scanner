This ExecPlan is a living document. The sections `Progress`, `Surprises &

## Purpose / Big Picture

Open IP Scanner 1.0.0 cannot be installed on Debian 13 because its Ubuntu
24.04 build recorded five Ubuntu-only Qt binary-package names. After this work,
the single Ubuntu-floor Debian package will retain automatically calculated ABI
version requirements while accepting the equivalent Qt package names used by
Ubuntu 24.04 and Debian 13. A clean-container gate will install, launch, and
remove the exact candidate on both systems before it can be uploaded or
attested.

## Surprises & Discoveries

- Observation: The published `open-ip-scanner_1.0.0_amd64.deb` requires
  `libqt6dbus6t64`, `libqt6gui6t64`, `libqt6network6t64`,
  `libqt6printsupport6t64`, and `libqt6widgets6t64`, none of which Debian 13
  provides.
  Evidence: `apt-get -s install` on Debian 13 rejects all five as not
  installable.
- Observation: A native Debian 13 CPack build resolves the same SONAMEs to the
  corresponding unsuffixed package names, while Ubuntu 24.04 uses the `t64`
  names. Both environments use `libqt6core6t64`.
  Evidence: the Debian build's `Depends` field contains `libqt6dbus6`,
  `libqt6gui6`, `libqt6network6`, `libqt6printsupport6`, and
  `libqt6widgets6`; the released Ubuntu build contains the `t64` variants.
- Observation: Existing lifecycle validation uses `--force-depends` against an
  empty dpkg database, so it proves unpack/configure/remove behavior while
  intentionally bypassing repository dependency resolution.
  Evidence: `scripts/validate-release-artifacts.sh` passes `--force-depends`
  to all three disposable dpkg operations.
- Observation: Debian 13 GCC emits `endbr64` instructions for the configured
  `-fcf-protection=full` flag, but Debian's final link omits the GNU IBT/SHSTK
  property that the existing release validator requires. The Ubuntu-built
  1.0.0 binary contains that property.
  Evidence: the local release gate passed all package checks then failed only
  `Control flow integrity: yes`; `readelf -n` showed only the x86-64 baseline
  property, while the downloaded 1.0.0 release showed IBT and SHSTK.

  packages.
  Rationale: This retains the documented download interface and the user's

## Context and Orientation

`CMakeLists.txt` defines the executable, install tree, and CPack DEB metadata.
CPack currently enables `CPACK_DEBIAN_PACKAGE_SHLIBDEPS`, which runs the host's
`dpkg-shlibdeps` and appends its distribution-specific package names to the
configured `iputils-ping` and `iproute2` dependencies.

`scripts/build-release-artifact.sh` performs two isolated release builds,
compares their package hashes, validates the selected package, builds the
source archive and SPDX document, and publishes the validated `.deb` beneath
the ignored `release/` directory. `scripts/validate-release-artifacts.sh`
checks the package metadata and payload. `.github/workflows/quality.yml` builds
the tested candidate on Ubuntu 24.04 after both supported build environments
pass, while `.github/workflows/release-artifacts.yml` builds and attests the
exact tagged release.

The package's executable links the Qt Core, D-Bus, GUI, Network, PrintSupport,
and Widgets shared-library SONAMEs. Ubuntu 24.04 and Debian 13 agree on those
SONAMEs and on `libqt6core6t64`, but use different binary-package names for the
other five modules. A Debian alternative relation, written `package-a |
package-b`, lets either supported repository satisfy the same dependency.

## Plan of Work

First, set version 1.0.1 and record a concise packaging correction in the
changelog, roadmap, platform contract, README packaging description, and
release checklist. Do not revise unrelated historical 1.0.0 evidence.

Second, add an executable Python wrapper around the system `dpkg-shlibdeps`.
It passes help/version calls through unchanged. For a dependency-generation
call it executes the real tool, requires exactly one dependency for each of
the five affected Qt modules, duplicates the original version relation on the
canonical `t64 | unsuffixed` alternatives, preserves all other output, and
fails without emitting a rewritten dependency field on malformed or ambiguous
input. A CPack project configuration sets CPack's DEB generator helper to this
wrapper so direct CPack and scripted builds share the policy.

Third, extend package validation to parse the final `Depends` field and require
the five alternatives with equal version relations, the common Qt Core
dependency, external commands, and compiler/runtime dependencies. Rename the
meaning of the force-depends test in diagnostics to payload lifecycle only.
Add a separate container validator that accepts exactly one package path and
uses Docker to install it with ordinary apt, confirm no linked library is
missing, run the existing offscreen startup smoke, remove it, and confirm the
binary is absent in both fixed supported base images.

Fourth, register focused normalization tests in CTest and extend the workflow
policy test. The Quality workflow will build and compatibility-test the package
on pull requests while uploading it only for non-pull-request events. The
release workflow will derive a semantic version from CMake, reject a mismatched
tag, run compatibility validation before attestations, and add a clean
verification job that downloads both artifact groups, checks SHA-256, and
verifies provenance plus the package's SPDX predicate before the workflow can
pass.

Finally, run all specified validation, obtain a fresh clean-context adversarial
review before commit, push the reviewed branch, and open the authorized draft
pull request. Stop for the repository owner's human verification and explicit
merge authorization. After that authorization, merge with a merge commit,
validate the exact main commit, rehearse the release workflow, tag the unchanged
commit as `v1.0.1`, wait for the tag workflow, independently download and check
its files, and create the GitHub Release with only the four verified assets.

## Validation and Acceptance

The normalizer is accepted when Ubuntu and Debian fixture outputs produce the
same ordered alternative package names while retaining their own version
relations, and every malformed or ambiguous case fails closed.

The package is accepted when its final control metadata contains exactly one
portable relation for each affected Qt module; the existing reproducibility,
hardening, license, payload, Lintian, source-bundle, checksum, and SPDX gates
pass; and ordinary apt installation plus offscreen launch and removal succeeds
for the exact same `.deb` in clean Ubuntu 24.04 and Debian 13 containers.

Publication is accepted only when the reviewed branch has been human-verified
and explicitly authorized for merge, every PR and main check passes, the
unchanged merge commit's tag workflow passes its clean attestation-verification
job, and the final GitHub Release exposes exactly the four verified assets from
that workflow.

## Idempotence and Recovery

Build and container validation use disposable or ignored directories and can
be rerun safely. The release publisher atomically replaces only the current
version's ignored local package. A transient workflow failure may be rerun for
the unchanged commit.

Do not move `v1.0.0` or overwrite its release. Do not push `v1.0.1` until every
pre-tag gate passes. If a pushed `v1.0.1` workflow reveals a source defect,
leave the tag immutable and prepare `1.0.2` through the full branch, validation,
review, human verification, and publication process.

## Interfaces and Dependencies

There are no application API, settings, scan, or data-format changes. The
external package interface remains one amd64 Debian file. The wrapper uses only
Python 3's standard library and the existing system `dpkg-shlibdeps`. The clean
install validator uses Docker only in jobs that advertise the supported-package
gate; normal build and test presets do not acquire a Docker dependency.
